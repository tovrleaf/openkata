# Create Skill

Create skills for this project. Skills can be either local (project-internal)
or distributable (shared via the dojo).

## Workflow

1. **Gather intent** — Ask the user what the skill should do. Collect:
   - A short name (lowercase, hyphenated, e.g., `run-tests`)
   - A one-line description of what the skill does
   - When the skill should activate (trigger conditions)
   - The workflow steps the skill should guide

2. **Determine placement** — Ask whether this skill is:
   - **Local** → `.agents/skills/<name>/` — internal to this project,
     not distributed
   - **Distributable** → `skills/<name>/` — shared via the dojo MCP
     server, symlinked into `.agents/skills/` for local use

3. **Check for conflicts** — List both `.agents/skills/` and `skills/`
   to ensure the name isn't already taken.

4. **Generate SKILL.md** — Create the SKILL.md in the target directory
   using the following skeleton as a starting point:

   ```markdown
   ---
   name: your-skill-name
   version: 1.0.0
   description: >
     One-sentence summary of what the skill does and produces. Use when
     the user wants to <trigger scenario>, needs to <another scenario>,
     mentions <keyword>, or asks about <related topic>.
   ---

   # Your Skill Name

   Brief intro sentence.

   ## Workflow

   1. **Step one** — Description.
   2. **Step two** — Description.

   ## Conventions

   - Key constraint or convention.
   ```

   Follow the style of existing skills in this project — see
   `release-kata` and `create-adr` for reference.

5. **Import to Tessl** — Run `tessl skill import <skill-directory>` to
   generate the `tile.json` required by the Tessl quality toolchain
   (ADR 0006).

6. **Symlink if distributable** — For skills placed in `skills/`, ask
   the user if they want it symlinked into `.agents/skills/` for local
   use. If yes:
   ```bash
   ln -s ../../skills/<name> .agents/skills/<name>
   ```

7. **Quality check** — Follow the `review-skill` workflow to lint,
   review, and optimize the new skill.

8. **Confirm** — Show the user the created skill and ask if adjustments
   are needed.

## Writing Principles

- **Be pushy with descriptions.** Agents undertrigger skills. Make descriptions
  slightly aggressive about when to activate — list many natural phrasings a user
  might say, including edge cases.
- **Explain the why, not rigid rules.** Avoid `ALWAYS` and `NEVER` in caps.
  Reasoning is more effective than blunt constraints because it lets the agent
  apply intent across novel situations.

## Project Conventions

- Local skills go in `.agents/skills/<name>/`
- Distributable skills go in `skills/<name>/` with a symlink in
  `.agents/skills/`
- Every skill must have a `tile.json` generated by `tessl skill import`
- Keep skills focused — one skill, one job
