# Ryu Create

Create artifacts for the OpenKata ryu. Each artifact type has its own file
format and directory convention.

## Artifact Types

| Type | File | Distributable dir | Local dir |
|------|------|-------------------|-----------|
| Skill (kata) | SKILL.md | `skills/` | `.agents/skills/` |
| Rule (dojo kun) | RULE.md | `rules/` | `.agents/rules/` |
| Role (sensei profile) | ROLE.md | `roles/` | `.agents/roles/` |
| Prompt (kata form) | FORM.md | `prompts/` | `.agents/prompts/` |

## Workflow

1. **Determine artifact type** — Ask what the user wants to create if
   not clear from context. Match to the artifact types above.

2. **Gather intent** — Collect:
   - A short name (lowercase, hyphenated, e.g., `markdown-consistency`)
   - A one-line description
   - For skills: trigger conditions and workflow steps
   - For rules: the conventions to enforce

3. **Determine placement** — Ask whether this artifact is:
   - **Local** → `.agents/<type>/<name>/` — internal to this project
   - **Distributable** → `<type>/<name>/` — shared via the dojo

4. **Check for conflicts** — List both local and distributable
   directories to ensure the name isn't already taken.

5. **Generate the artifact** — Create the appropriate file in the
   target directory. For skills, use this skeleton:

   ```markdown
   ---
   name: your-skill-name
   version: 1.0.0
   description: >
     One-sentence summary of what it does. Use when the user wants to
     <trigger scenario>, needs to <another scenario>, mentions <keyword>,
     or asks about <related topic>.
   ---

   # Your Skill Name

   Brief intro sentence.

   ## Workflow

   1. **Step one** — Description.
   2. **Step two** — Description.
   ```

   For rules, use a simpler structure (no frontmatter required):

   ```markdown
   # Rule Name

   Brief description of what this rule enforces.

   ## Conventions

   - Convention one
   - Convention two
   ```

   Follow the style of existing artifacts in this project.

6. **Create CHANGELOG.md** — Every artifact gets a changelog starting
   at v1.0.0 with an initial `### Added` entry.

7. **Import to Tessl** (skills only) — Run
   `tessl skill import <skill-directory>` to generate `tile.json`
   (ADR 0006).

8. **Symlink if distributable** — For artifacts in distributable
   directories, ask the user if they want it symlinked into the
   corresponding `.agents/` directory. If yes:
   ```bash
   ln -s ../../<type>/<name> .agents/<type>/<name>
   ```

9. **Quality check** (skills only) — Follow the `review-skill` workflow
   to lint, review, and optimize.

10. **Confirm** — Show the user the created artifact and ask if
    adjustments are needed.

## Writing Principles

- **Be pushy with descriptions.** Agents undertrigger skills. Make
  descriptions slightly aggressive about when to activate — list many
  natural phrasings a user might say, including edge cases.
- **Explain the why, not rigid rules.** Reasoning is more effective than
  blunt constraints because it lets the agent apply intent across novel
  situations.

## Project Conventions

- Local artifacts go in `.agents/<type>/<name>/`
- Distributable artifacts go in `<type>/<name>/` with a symlink in
  `.agents/<type>/`
- Every skill must have a `tile.json` generated by `tessl skill import`
- Every artifact gets a CHANGELOG.md
- Keep artifacts focused — one artifact, one job
